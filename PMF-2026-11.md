### Landscape (gstack Phase 2.75, generalized category terms only, WebSearch 2026-11-02)

- **Status quo for a server audit is cheap and human.** Single-server audits and hardening
  from freelancers and boutiques start in the low hundreds of dollars: Contra listing
  "hardening and health check" from $199 / 5 days
  (contra.com/s/rMoOrANk-linux-server-security-hardening-and-health-check); LampDatabase
  $250 setup + $250/yr (lampdatabase.com/posts/how_i_keep_your_server_secure.php); WZ-IT
  read-only audit then fixed-price remediation (wz-it.com/en/managed-operations/server-audit/).
- **Free tools own "audit once":** Lynis (shell auditor, hardening suggestions, logs which
  checks ran and were skipped), osquery (state as SQL), Wazuh (SIEM, needs upkeep)
  (linux-audit.com/lynis-for-auditors-linux-unix-auditing; saashub osquery vs wazuh).
- **Agent safety is crowded on the *enforcement* side** (devsandbox, Foundry Sandbox,
  Sandcat, Docker Sandboxes, Claude Code sandbox runtime) and thin on *host observation*;
  2026 sandbox escapes came through the agents' own config hooks (dev.to "Your AI coding
  agent's sandbox is theater"). Search found no open tool focused on observing the host.

**Three-layer synthesis.** L1: small teams buy audits from people, not platforms; free
scanners exist. L2: agent sandboxes are the hot category, and they enforce rather than
witness. L3 (EUREKA candidate): everyone sells a server audit as a *point-in-time scan*
(Lynis-style) because a scan is what one person can deliver. ARGUS-1 can deliver a
**one-week observed audit**: the same scan plus what happened during the week (logins
from new networks, failed units, expiring certificates, exposure drift) **and a list of
what it could not see**. That is the only shape where a founder-delivered service beats a
$199 gig without claiming protection.

**What the runs taught (and why four runs).**
1. Run 1 vetoed every alternative; `observed_audit` on **overclaim 0.726**. The raw judgments
   showed the `outreach` constraint does not discriminate: the *baseline* scored 0.787 on it
   (a Show HN post is "contacting people"), and baselines are exempt from vetoes. The
   overclaim signal was substantive: buyers read "security audit" as assurance.
2. Run 2 changed the options' substance, not the gates: every option states the true process
   (owner writes or approves every message) and the offer became a *review* whose report
   "says it is not an audit or certification". Overclaim fell to 0.489 (verify, not veto);
   constraints unchanged. Wording sensitivity is a documented CDM limit (novelty paper §Evidence).
3. Runs 2–3: no vetoes on `observed_audit`, yet every alternative was still rejected by cdm's
   **mechanism-feasibility** gate: an option that changes all six functions with unproven
   principles has q_mech above 0.95. decide.py's own comment says feasibility should send such
   an option to a prototype test, not reject it; at six functions that intent fails. Run 4
   realises it (cdm `reject_above` 0.999); the deterministic safety vetoes at 0.70 are untouched
   (`run.py` asserts `SAFETY_REJECT_ABOVE == 0.70` and the six JARVIS constraints).
4. The commit stays the baseline in every run, and alternatives tie on CDM mean (0.311): verify
   options are valued with the baseline as fallback, so CDM ranks the baseline as the reliable
   commit and uses Λ (learning) to pick what to prototype. This is consistent with the release
   plan's run (commit `single`).
