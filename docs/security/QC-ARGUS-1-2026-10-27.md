# ARGUS-1 quality control — 2026-10-27

Owner direction: ARGUS-1 (formerly JARVIS) is the core of Archymedes; it must be
excellent on Windows and Linux and real users must have no issues. This is the
measured state, what was fixed today, and what stands between the product and
general users. Evidence is file:line or a measurement; nothing here is assumed.

## Verdict

**Not yet ready for general users.** It is a strong single-machine monitor on
the machine it was built on. It is not yet a product a stranger can install,
understand, update and remove on Windows or Linux. Four blockers, below, are
each days of work, not a patch.

## Blockers for general users

1. **No single install, update and uninstall path.**
   - **Windows:** QUICKSTART.md:3-29 offers WSL or native mode. The sealed runtime needs a Linux root step (`deploy_root_runtime.py --enable`).
   - **Linux:** `install.sh`, the root sealed runtime and the Argus `.deb`/`server/install.sh` are three separate paths. The Argus ones live in `~/archymedes-site`, not in this repo.
   - **Updates:** these are dated owner command sheets.
   - **Uninstall:** none for the main product.
2. **Never installed on a machine other than this one.**
   - The Argus Windows unattended installer is "not exercised end to end" (ARGUS-FULL-INSTALL-2026-10-22.md:22-29).
   - Native Windows mode (no WSL) is `unverified` in the assurance register (`jarvis/core/assurance.py:34`), with about 300 POSIX-assuming tests.
   - Plain Linux is "source-tested only" in the same entry. That contradicts an archymedes-site commit claiming a verified clean-server install, so one of the two is stale.
3. **Alert quality a new user cannot live with.** The live dashboard shows 46 critical and 61 high findings:
   - **Double counting:** secrets findings appear once from `secrets` and again from `ledger` ("unresolved for 4d: …"). That is 9 of the criticals.
   - **Blocklist false positives at critical:** "contacted a known attacker IP" fires for 142.251.38.238 (Google, `1e100.net`) and 35.190.43.134 (Google Cloud). btweb.exe hits 286 listed IPs (torrent peers).
   - **Category confusion:** `gaps` shows ARGUS-1's own ATT&CK coverage gaps ("T1001 Data Obfuscation") as *high findings* about the machine.

   Changing any of this changes the score, so under the score-integrity rule each needs a proven detector-bug write-up or your decision. None was changed today.
4. **Local API reachable by same-user malware.**
   - `GET /` hands the write token to any local caller (`jarvis/web/server.py:821-824`).
   - Requests with no `Origin` header pass the origin check (`server.py:444-445`).

   Browsers and other accounts are blocked, but any process running as the user can trigger runs and fixes. `token.py` calls the token "a gate, not a wall".

   **Narrowed 2026-11-08 (fix/cr-sec), not closed.** The cookie now goes only to accounts that can already read the token file (the daemon's account and root; no longer `JARVIS_OWNER_UID`), and only on a browser navigation (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Site: none|same-origin`). A POST whose only credential is a cookie needs `Sec-Fetch-Site: same-origin` or the loopback `Origin`; header-token clients (CLI, desktop app, supervisors) are unchanged. What this closes: under the service account, a process running as the owner can no longer get the write token from `GET /` (the owner's browser pairs through `/pair` instead); and tools or confused deputies that fetch a URL without choosing its headers get no cookie and cannot replay one. What remains: in the default install the daemon runs as the user, so same-user malware reads `~/.jarvis/api.token` and sends it as a header; fetch metadata is forgeable by a local process; a paired client token or browser cookie the owner saved is readable by the owner's processes. Tests: `tests/test_api_hardening.py` (`DashboardCookieTests`, `CookieCredentialTests`), `tests/test_api_clients.py`.

## Major

- **WSL distro name hardcoded as "Ubuntu"** in about six shipped files, including `jarvis/platform/provenance/persistence.py:31,78,91,138,143`, `install.sh:246,274` and the two supervisors. A user whose distro is "Ubuntu-24.04" or "Debian" gets ARGUS-1's own tasks reported as critical tampering.
- **Desktop app never installed.** The installer needs a self-built binary (`install.ps1:85`), and the binary is unsigned.
- **Python version not checked by `install.sh`.** `pyproject.toml` requires 3.12; Debian 12 ships 3.11 and fails at runtime, not at install.
- **Linux installer prints Windows steps on plain Linux** (`install.sh:230`). `README.md:3` frames the product as WSL + Windows.
- **UAC prompts are spread across documents.** `quickstart.ps1:16` says "No elevation required"; declining a later prompt quietly reduces coverage.
- **Machine reliability dominates coverage.** There were 37 Windows hard resets in 14 days on this machine. That's hardware or firmware, not ARGUS-1, but the product should tell the user rather than silently lose hours.

## Minor

- Internal names still say jarvis: the package, CLI, tasks, service, `local.jarvis.desktop` and some prompts (for example `jarvis-health-monitor.ps1:240`). Users still type `jarvis …`. Renaming the CLI and tasks is a migration with its own release, because task fingerprints are pinned.
- `procs.html`/`procs.js` show the new name only once the procs-identity release (staged 10-24) is deployed and restaged, because it owns those files.
- An Argus server's deadman heartbeat is opt-in, so a server is unwatched until configured.

## Recommended order

1. **Alert quality (blocker 3).** Fix double counting as a detector bug with a replay. Move `gaps` to a coverage view, not findings. Require a second signal before any blocklist-only hit is critical. This needs your sign-off per score-integrity.
2. **One installer per platform (blocker 1)** with install, update and uninstall, folding in the Argus scripts from `~/archymedes-site`.
3. **Clean-machine validation (blocker 2)** in disposable VMs:
   - **Linux:** the existing QEMU lab (`jarvis/lab/vmlab.py`) can run Ubuntu 24.04 and Debian 12.
   - **Windows:** needs Windows Sandbox or a VM, which you'd enable.
4. **API authentication (blocker 4).** A per-user token file with owner-only ACLs instead of a cookie from `GET /`.
5. **Distro discovery** instead of "Ubuntu", plus a Python check in `install.sh`.
